Analyzers

ClawGuard uses 6 analysis layers to catch threats that any single technique would miss. Each layer targets a different class of attack.

Overview

Analyzer Speed Requires What It Catches
Static ~30ms Nothing Code patterns, obfuscation, dangerous functions
Dependency ~300ms Network (optional) Malicious packages, typosquats, install scripts
Prompt Injection ~10ms Nothing Instruction overrides, hidden unicode, homoglyphs
Semantic 3-15s API key Malicious intent, capability abuse, social engineering
Attack Chains ~100ms Multiple skills Dangerous capability combinations across skills
Sandbox 5-30s Docker Runtime credential theft, network exfiltration

Static Analyzer

The static analyzer scans all code files using 60+ regex patterns defined in patterns/code.yaml. It also performs obfuscation detection and AST (Abstract Syntax Tree) analysis for JavaScript files.

Scanned File Types

JavaScript (.js, .mjs, .cjs, .jsx, .tsx), TypeScript (.ts, .mts), Python (.py), Shell (.sh, .bash, .zsh), Ruby, Perl, PHP, Go, Rust, Markdown, YAML, JSON, TOML, and config files.

Detection Categories

ID Category Examples
T-CODE-001 Malicious commands curl | bash, wget | sh, silent curl + execute
T-CODE-002 Obfuscation base64 decode + exec, eval(atob(...)), hex encoding, _0x variables, JS packers
T-CODE-003 Fetch and execute fetch().then(eval), dynamic require(), dynamic import()
T-CODE-004 Credential access process.env.*KEY, .ssh/id_rsa, .aws/credentials
T-PERSIST Persistence >> .bashrc, crontab, systemd services, git hooks

T-CODE-007 Destructive commands rm -rf, sudo

Obfuscation Detection

Beyond regex patterns, the static analyzer detects:

  • Non-printable characters — control characters that may hide code
  • Invisible unicode — zero-width joiners, BOM, etc.
  • Extremely long lines — common in obfuscated/packed code
  • JavaScript packers — eval(function(p,a,c,k,e,... patterns
  • _0x obfuscation — heavy use of _0x-prefixed variables with density analysis to distinguish minified code from malware

AST Analysis

For JavaScript files (.js, .mjs, .cjs, .jsx), ClawGuard also parses the file into an AST using Acorn and performs structural analysis for suspicious patterns that regex cannot reliably match.

Dependency Analyzer

The dependency analyzer checks package dependencies against a database of 100+ known-malicious packages and detects typosquatting using Levenshtein distance and dnstwist-inspired techniques.

Supported Package Managers

  • npm — parses package.json (dependencies, devDependencies, peerDependencies, optionalDependencies)
  • pip — parses requirements.txt and pyproject.toml
  • Go — parses go.mod (require blocks and single requires)

Detection Methods

Known Malicious Packages

The database in patterns/deps.yaml contains 100+ npm, 40+ pip, and 5+ Go packages known to be malicious, with specific version ranges. Examples include the event-stream supply chain attack, ua-parser-js compromise, and dozens of typosquat packages.

Typosquat Detection

For every dependency, ClawGuard computes the Levenshtein distance against a list of popular packages. A distance of 2 or less triggers an alert. This catches attacks like crossenv (targeting cross-env) and d3.js (targeting d3).

Registry Checks (when network is available)

  • Package existence — flags packages not found on npm/PyPI
  • Install scripts — flags preinstall/install/postinstall hooks
  • New packages — flags suspiciously new packages with low download counts
  • Deprecated/yanked — warns about deprecated npm packages and yanked PyPI versions

Install Script Analysis

ClawGuard inspects package.json install scripts for dangerous patterns: curl | bash, eval(), base64 -d, command substitution, and inline node -e / python -c execution.

Programmatic Checks

These go beyond regex to detect attacks that are invisible to the human eye:

  • Invisible Unicode Detection — scans for 40+ invisible characters including zero-width spaces, zero-width joiners, word joiners, directional marks, Mongolian vowel separators, and various Unicode space characters
  • Homoglyph Detection — identifies Cyrillic, IPA, fullwidth, and mathematical characters that look identical to ASCII but can evade keyword filters (e.g., Cyrillic "a" vs Latin "a")
  • RTL Override Detection — catches Right-to-Left Override (U+202E) and related bidirectional control characters that can reverse the visual order of text, hiding malicious instructions
  • Hidden Whitespace — detects excessive consecutive spaces (10+), excessive newlines (6+), and tab-space mixtures that may conceal instructions

Semantic Heuristics

The prompt analyzer also runs lightweight semantic checks:

  • Capability mismatch — flags "simple" skills that request dangerous permissions
  • Instruction sentiment shift — detects documents that start helpful but shift to override-like instructions
  • Cross-session references — flags instructions that reference other users or sessions

Semantic Analyzer

The semantic analyzer uses a Large Language Model to understand a skill's intent, not just its patterns. It catches attacks that are invisible to regex and static analysis.

Requires API Key

Semantic analysis requires a configured AI provider (Anthropic, OpenAI, or Ollama). Run clawguard config to set one up, or skip with --fast.

Multi-Provider Support

Provider Default Model Notes
Anthropic Claude Sonnet 4 Best accuracy for threat detection
OpenAI GPT-4o Fast analysis, good accuracy
Ollama (local) Llama 3 70B Free, private, no API costs

Threat Categories Analyzed

The LLM evaluates the skill for 10 threat categories:

  1. Instruction Override — attempts to override the agent's core instructions or bypass safety guidelines
  2. Credential Theft — reading SSH keys, AWS credentials, API tokens, or passwords
  3. Data Exfiltration — sending data to external servers, webhooks, or unauthorized recipients
  4. Persistence — cron jobs, startup scripts, git hooks, systemd services
  5. Privilege Escalation — unnecessary use of elevated privileges
  6. Deception — hiding actions from the user or deceiving the agent
  7. Capability Abuse — requesting capabilities that don't match the stated purpose
  8. Social Engineering — persuasion techniques that manipulate the agent into unsafe actions
  9. Delayed Attack — time-based or condition-based triggers for later activation
  10. Memory Poisoning — corrupting the agent's memory or context over time

How It Works

The semantic analyzer gathers all skill content (SKILL.md, package.json, requirements.txt, up to 10 script files, and 5 config files), sends it to the LLM with a security-focused prompt, and receives structured JSON findings with severity, evidence, and attack scenarios.

It also detects capability-purpose mismatch: when a skill's stated purpose (e.g., "weather lookup") doesn't align with its actual capabilities (e.g., reading SSH keys).

Attack Chain Analyzer

The attack chain analyzer is unique to ClawGuard. It scans multiple skills together to find dangerous capability combinations that would not be flagged when analyzing skills in isolation.

Why This Matters

Two perfectly innocent skills can form a lethal attack chain. Skill A reads ~/.ssh/id_rsa (a "backup" tool). Skill B sends data via messaging (a "digest" tool). Together, they create a complete credential exfiltration pipeline.

Capabilities Tracked

The analyzer maps each skill's capabilities across 10 categories:

  • file_read — reading files, dotfile access
  • file_write — writing files, shell config modification
  • network_out — outbound HTTP/HTTPS, fetch, curl, webhook
  • network_in — listening servers, sockets
  • exec — shell command execution, child_process
  • messaging — Discord, Slack, Telegram, email, SMS
  • browser — Puppeteer, Playwright, Selenium
  • cron — scheduled tasks, intervals
  • env_access — reading environment variables, API keys
  • credential_access — SSH keys, AWS creds, .netrc, .npmrc

Dangerous Chain Types

Chain Required Capabilities Severity
Credential Exfiltration credential_access + network_out Critical
File Exfiltration via Messaging file_read + messaging Critical
Persistent Backdoor network_in + exec Critical
Credential Harvesting + Persistence credential_access + file_write High
Browser Session Theft browser + network_out High
Scheduled Malicious Execution cron + exec High
Environment Variable Theft env_access + messaging High
Stealth Data Collection file_read + file_write Medium

$ clawguard library ~/.skills/
$ clawguard graph ~/.skills/ # visual capability graph

Behavioral Sandbox

The sandbox analyzer is the ultimate test: it runs the skill in an isolated Docker container with planted honeypot credential files and monitors every file access, network connection, and command execution.

Zero False Positives

If a skill accesses honeypot credentials during execution, that is definitive proof of credential theft behavior. No amount of obfuscation or clever wording can evade runtime monitoring.

How It Works

  1. Build sandbox image — creates an isolated Docker container with Node.js, Python, strace, tcpdump, and inotify-tools
  2. Plant honeypot credentials — places fake credential files in standard locations
  3. Execute skill — runs the skill's scripts under strace monitoring
  4. Analyze behavior — checks for honeypot access, suspicious network activity, and dangerous commands

Honeypot Files

Path Content
/root/.ssh/id_rsa Fake SSH private key with HONEYPOT marker
/root/.ssh/id_ed25519 Fake ED25519 key with HONEYPOT marker
/root/.aws/credentials Fake AWS access key and secret
/root/.config/gcloud/credentials.json Fake GCP service account credentials
/root/.env Fake API keys and secrets
/root/.netrc Fake GitHub credentials
/root/.npmrc Fake npm auth token

Monitoring

  • strace — traces all open, openat, read, connect, and execve system calls
  • inotifywait — watches honeypot directories for any file access
  • tcpdump — captures all DNS queries and network connections

Usage

$ clawguard scan ./my-skill --sandbox
Requirements

Docker must be installed and running. The sandbox image is built automatically on first use (~30 seconds), then cached for subsequent runs (~5 seconds).

Risk Scoring

All findings from all analyzers are aggregated into a single risk score using severity-based weights:

SEVERITY_WEIGHTS = {
  critical: 25,
  high:     10,
  medium:   4,
  low:      1,
  info:     0
}

RISK_THRESHOLDS = {
  SAFE:     10,   // score <= 10
  LOW:      25,   // score <= 25
  MEDIUM:   50,   // score <= 50
  HIGH:     75,   // score <= 75
  CRITICAL: 100  // score > 75
}

The formula is simple: sum each finding's severity weight, capped at 100. For example:

  • 1 critical (25) + 2 high (20) + 1 medium (4) = 49 → MEDIUM
  • 3 critical (75) + 1 high (10) = 85 → CRITICAL
  • 2 low (2) + 1 info (0) = 2 → SAFE
